# Project Docs（项目文档）

> 本文件是 `SKILL.md` 的中文对照稿，方便阅读和修改。正式启用技能前，请把确认后的改动同步到 `SKILL.md`。

帮助项目成员和未来贡献者通过少量、准确的文档理解项目。遵循仓库已有的文档约定。

## 先核实事实

- 先阅读相关项目指南和现有文档；再检查源代码、配置、测试或其他权威资料，核实文档中的说法。
- 明确文档面向谁，以及读者需要了解或完成什么。如果这点不明确且会实质改变文档内容，就先询问；否则做出合理选择并简要说明。
- 只描述当前且已核实的行为和结构。尚未确认的内容应明确标注，不要猜测补全。

## 写给人看

- 开头先讲目的和实用信息。使用清楚易懂的语言，解释必要术语，只保留读者理解问题所需的架构或实现细节。
- 只建立最少但够用的文档。项目已有 README 时，用它作为简洁入口；只有在独立页面确实有帮助时才拆分并链接。
- 每条事实只在一个权威位置维护。避免重复解释、任务流水账、推测性计划，以及过长的禁止事项或免责声明。

## 区分当前状态与历史

- 项目指南和架构文档应聚焦项目现在的工作方式。不要把它们写成变更日志，也不要把已被取代的方案写得像仍然有效。
- 如果需要保留长期有效的决策或其权衡，单独写成架构决策记录（ADR），或遵循仓库现有的决策记录格式；只在有帮助的地方链接。不要为每个日常变更都新建决策记录。

## 审查和维护

- 将现有文档与已核实的项目现状对照。修正过时内容和失效链接；合并明显重复的内容，不要顺带重写无关部分。
- 编写项目概览、架构/设计文档、规则或术语表时，应根据读者需要选择结构，不要强迫所有文档套用同一模板。
- 编辑后，重新对照来源核查改动过的说法和链接。汇报修改了哪些文件，以及仍未核实的重要事实。
